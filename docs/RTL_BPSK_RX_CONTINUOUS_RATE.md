# BPSK RX: подача кадров без пауз

Ниже сначала сохранены измерения исходного RX с двумя буферами. Далее сохранена историческая приёмка третьего буфера; актуальные результаты ускорения захвата acq1 и команды куратора приведены в конце.

## Эксперимент

Приёмник `bpsk_rx` получил по четыре кадра длиной 192, 768 и 2048 символов при каждой полярности сброса. Источник держит `s_valid=1` от первого до последнего принятого отсчёта, в том числе между кадрами, и удерживает входное слово при `!s_ready`. `m_ready=1`. Существующий числовой тестбенч сверяет каждый выход и каждый результат захвата с Python fixed-моделью; сохранены исходные векторы, включая шумный четвёртый кадр. Интервалы измерены в тактах симуляции, без утверждения о частоте FPGA.

Для измерения произвольных пауз скрипт [bpsk_rx_continuous_rate.py](../tools/bpsk_rx_continuous_rate.py) создаёт в новом выходном каталоге копию существующего тестбенча и убирает **только** его исторический запрет входной паузы свыше 32 тактов. Остальные проверки и scoreboard сохраняются. Наблюдатель [bpsk_rx_rate_tb.sv](../rtl/tb/bpsk_rx_rate_tb.sv) проверяет непрерывный offer, удержание при паузе и 32 такта внутреннего FIR-хвоста после каждого принятого `s_last`. Он суммирует блокировки по состоянию `tail`, не приписывая их конкретному другому блоку. Файлы реализации приёмника не менялись.

## Измерения Questa

Обе полярности сброса дали одинаковые результаты. Межкадровый промежуток — число тактов без принятой передачи между последним словом одного кадра и первым словом следующего. Промежутков три; заключительный хвост тоже проверен, но не включён в число блокировок источника, который уже закончил подачу.

| Символов в кадре | Принято входных отсчётов | Паузы из-за FIR-хвоста | Остальные паузы | Межкадровый промежуток |
| ---: | ---: | ---: | ---: | ---: |
| 192 | 6299 | 96 | 975 | 32…643 |
| 768 | 24731 | 96 | 0 | 32 |
| 2048 | 65691 | 96 | 0 | 32 |

Во всех шести прогонах четыре захвата и все 768 / 3072 / 8192 выходных символа соответственно совпали с fixed-моделью. Два отрицательных контроля на 768 символах требуют отказа scoreboard с тегом `[NUMERIC]` и кодом завершения 13. Два теста валидатора с восемью подтестами отвергают неполные и противоречивые сводки.

Исходные логи, векторы, созданная копия scoreboard и [результаты](bpsk_rx_continuous_20261029_results.json) сохранены в `build/bpsk_rx_continuous_20261029/`; это отдельный эксперимент, а не новая полная приёмка с проверкой хешей. Обычные исторические свидетельства не перезаписывались.

Синхронная пауза на 32 такта после каждого кадра следует из самого `bpsk_rx`: при `tail != 0` он деактивирует `s_ready`. Поэтому поток, который обязан непрерывно подавать отсчёт каждый такт и не допускает обратного давления, невозможно обслуживать бесконечно долго конечной очередью при конечных кадрах. Остальные 975 тактов для коротких кадров измерены только в данном четырёхкадровом наборе; верхняя граница для других нагрузок не исследована. `costas_stream` в этот приёмник не интегрирован; текущая обработка включает собственную совместную цепь Gardner/Costas/AGC. Физическая частота, поведение других профилей и непрерывный сквозной темп не подтверждены.

## Причина дополнительных пауз: повторный прогон

В отдельном повторном прогоне наблюдатель на каждом принятом фронте с `s_valid && !s_ready && tail==0` требует `configured=1`, `error=0`, `capture_active=0`, `input_count=0` и `occupied[next_capture]=1`. Для кадров 192 это подтверждено на **всех 975 дополнительных тактах** при обеих полярностях. Из них 973 пришлись на состояние `TRACKING`, два — на `RETIRE`; в `WAIT_FRAME` и `ACQUIRING` таких тактов не было. На кадрах 768 и 2048 дополнительных блокировок не было.

При отсчёте кадров с нуля буфер 0 удерживал начало кадра 2 на 364 такта, а буфер 1 — начало кадра 3 на 611 тактов. Логи показывают завершение `TRACKING`, затем `RETIRE` соответствующего буфера, затем приём на следующем такте. Наблюдаются именно состояния автомата, а не время отдельных арифметических операций внутри tracking. Повторно прошли все шесть прогонов с числовым scoreboard и два отрицательных контроля; валидатор проверяет суммы состояний, интервалы блокировок и порядок событий захвата, слежения и освобождения. В отдельном [результате](bpsk_rx_continuous_states_20261029_results.json) сохранены полные события; исходный результат первого прогона не изменялся. Это наблюдение не устанавливает задержку для произвольных кадров, начальных условий и нагрузок.

Воспроизведение с установленными Questa и UVM:

```sh
python3 tools/bpsk_rx_continuous_rate.py --output <local-tmp>
python3 -m pytest -q tests/test_bpsk_rx_continuous_rate.py
```

Выходной каталог должен отсутствовать: запуск ничего в нём не перезаписывает. Симулятор может требовать запуска вне ограниченной песочницы.

## Изменение: третий короткий буфер — Questa PASS (2026-10-29)

Таблица и логи выше относятся к исходному RX с двумя буферами. Новая реализация сохраняет две полные памяти и добавляет `SHORT_SAMPLES=2048` комплексных слов по 36 бит. В `bpsk_samples` это четыре независимых банка 512×36 с синхронным чтением; арифметика и латентность интерполятора 7 тактов прежние.

Гарантия размера получается из существующего протокола, а не из предположения о канале: `cfg_count` принимается вместе с последней из 192 меток конфигурации, задаёт `N` и не меняется при занятости любого буфера. Входной кадр обязан иметь `8N…8N+64` отсчётов, включая хвост TX и задержку канала. RX дополнительно записывает 32 нуля FIR. Поэтому короткий буфер разрешён только при `8N+96 ≤ SHORT_SAMPLES`: для N=192 нужно максимум 1632 слова; 2048 — следующая степень двойки. Для значения по умолчанию проходят N=192…244, N=245 уже использует только полные буферы. Граница определена до первого входного handshake. При отсутствии принятой конфигурации приём вообще запрещён.

Для подходящей конфигурации оба указателя следуют 0→1→2→0, для остальных 0→1→0. Занятый следующий буфер блокирует приём первого слова, указатель не перескакивает через него. Захват, обработка и выдача кадров сохраняют один порядок. Переконфигурация пустого RX начинает оба кольца с 0, в том числе при переходе от короткой к длинной конфигурации. Сброс любой полярности снимает занятость всех трёх буферов, отменяет capture/tail/выход и требует конфигурацию заново; RAM не очищается.

Отсутствие `s_last` на принятом отсчёте `8N+64` принудительно завершает кадр с `invalid` и sticky `error`, после чего принимаются только внутренние 32 нуля. Внешние входы запрещены до сброса; поздний `s_last` не принимается. Ранний `s_last` ниже `8N` также даёт прежнюю ошибку. Таким образом, даже нарушитель протокола не может записать более `8N+96` слов. Отдельное разрешение записи короткой RAM дополнительно проверяет физический индекс `< SHORT_SAMPLES`, исключая циклическую перезапись. Префикс уже начавшего декодироваться ошибочного кадра не отзывается; `error` запрещает считать его успешно принятым.

Оценка памяти: добавлено 2048×36 = **73 728 бит (9 КиБ)**; суммарная sample RAM — 1 271 808 бит (два раза 16640×36 плюс короткий буфер), дополнительно восемь 42-битных накопителей энергии и управляющие регистры. Четыре банка 512×36 ориентировочно требуют **4 RAMB18 = 2 BRAM-тайла** Artix-7 или **8 M10K** Cyclone V. Относительно сохранённых отчётов BPSK это около **47/50 тайлов** и **199/397 M10K**. Это оценка, размещение и тайминг 100 МГц новой версии не измерены; Vivado/Quartus не запускались.

Обновлённый наблюдатель печатает резервирование каждого кадра и события обработки с двухбитным номером буфера. Валидатор сверяет фактические назначения с разрешённым кольцом, запрещает повторное использование до `RETIRE`, проверяет порядок всех захватов/выходов, суммы пауз и освобождение заблокированного буфера. Новый набор:

- Пачки **4×192, 4×768, 4×2048**, обе полярности: `other_blocked=0`, `min_gap=max_gap=32`, `tail_blocked=96`, `tail_checks=128`; все выходные поля и захваты побитно совпадают с fixed-моделью.
- Серия **16×192**, обе полярности: `other_blocked>0` обязательно, чтобы подтвердить исчерпание третьего буфера; все 3072 символа и 16 захватов совпадают с моделью, потерь/перестановок нет. Обязательные хвостовые блокировки — 480 тактов, проверок хвоста — 512.
- Отрицательный численный контроль 768: `[NUMERIC]`, код 13, без положительного PASS.
- `bpsk_rx_buffers_tb`: точное заполнение 2048 слов при N=244, отказ от короткого банка при N=245, запрет конфигурации при занятом только третьем банке, запрет при заполненных трёх банках и остановленном выходе, переход между конфигурациями с разными кольцами без сброса, поздний/отсутствующий и ранний TLAST, сброс в середине короткого capture и FIR-хвоста. Обе полярности, итог `PASS BPSK RX buffer guards`.
- Блочный scoreboard `run_bpsk.py`: все три номера памяти, все четыре банка, стык main/tail двух полных буферов, граница короткой RAM и нулевое дополнение, включая остановки `ce`.

Команды куратора из корня репозитория; все указанные каталоги должны отсутствовать:

```sh

python3 tools/run_bpsk.py --suite all --output build/bpsk_rx_short3_all_20261029_review1
python3 tools/run_bpsk_uvm.py --suite all --pilot rx --profile all --output build/bpsk_rx_short3_uvm_rx_20261029_review1
```

`--output` добавлен обоим общим runner'ам; `run_bpsk.py` также передаёт отдельный путь отчёту `bpsk_precision.py`, чтобы вложенный запуск не переписывал старое свидетельство. Прежние пути по умолчанию сохранены для совместимости; приведённые команды используют только новые пути. Полный численный и UVM-набор должен сохранить обе полярности, backpressure, reset внутри кадра, все профили общего RX, RTL loopback и отрицательные контроли. До выполнения этих команд утверждения о новых Questa PASS не делаются. Синтез остаётся на паузе; CURRENT_STATUS/DIARY не обновляются.

Результат Questa для третьего буфера (`build/bpsk_rx_short3_rate_20261029_review3/results.json`, PASS, обе полярности): 4×192 — дополнительная блокировка **0** вместо прежних 975 тактов, промежутки ровно 32 такта FIR-хвоста; 4×768 и 4×2048 — 0, без регрессии; длинная серия 16×192 — 6147 тактов блокировки (максимальный промежуток 651), все 3072 символа и 16 захватов совпали с fixed-моделью. Устойчивый поток кадров 192 символа третьим буфером не обеспечивается: для него нужен захват не дольше ≈722 тактов (сейчас 1341).


## Ускорение захвата acq1: Verilator PASS (2026-10-29)

Исторические данные выше относятся к захвату A=1341. Текущий `bpsk_acquire` даёт **A=677** для BPSK; этапы и все четыре группы профилей — в [BPSK_RTL.md](BPSK_RTL.md#захват-ускорение-acq1-2026-10-29). Межкадровые границы и 32 такта FIR сохранены. Критерий `series_192` теперь требует `other_blocked=0` и `min_gap=max_gap=32`. Добавлена серия `series_192_d0`: 16 кадров минимальной разрешённой длины 1536. Генератор `receiver_vectors(..., frame_padding=0)` обрезает входную pin-waveform до `8N`, после чего заново вычисляет весь эталон; захват/выходы не берутся из более длинного кадра.

Каждый `RX ACQUISITION start=… done=… A=…` измеряется по принятому start и наблюдаемому родителем done. Валидатор требует по одному измерению на кадр, проверяет разность тактов, порядок, отсутствие перекрытия и бюджет A≤686. В `results.json` у каждой строки есть `acquisition_cycles`, `a_min`, `a_max`, `queued_processing_period=A+882`.

Измерено **Verilator 5.050**, обе полярности сброса:

| Сценарий | Принято отсчётов | Захватов / выходных символов | tail_blocked / tail_checks | other_blocked | min_gap / max_gap | A |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 4×192 | 6299 | 4 / 768 | 96 / 128 | **0** | **32 / 32** | 677 |
| 4×768 | 24731 | 4 / 3072 | 96 / 128 | **0** | **32 / 32** | 677 |
| 4×2048 | 65691 | 4 / 8192 | 96 / 128 | **0** | **32 / 32** | 677 |
| 16×192, штатные d=(36,39,44,36) | 25196 | 16 / 3072 | 480 / 512 | **0** | **32 / 32** | 677 |
| 16×192, d=0 | 24576 | 16 / 3072 | 480 / 512 | **0** | **32 / 32** | 677 |

Локальные логи, векторы, копии scoreboard и сводка окончательного снимка: `<local-tmp>`. Все поля выходов и захватов совпали побитно с `psk_fixed`; прошли два отрицательных контроля 768 и buffer guards обеих полярностей. Воспроизведение: `python3 tools/bpsk_rx_continuous_rate.py --backend verilator --output <local-tmp>`. Старые свидетельства `build/` не изменялись.

Конечная серия сама по себе не доказывает бесконечный поток. Для BPSK при N=192 и постоянно готовом выходе T=879. По потактовой рекуррентности исследования (F — первый входной отсчёт, D — наблюдаемый acquisition_done, R — первый фронт повторного использования буфера):

```text
L_i = 1536+d_i, 0≤d_i≤64
F_i = max(F_(i-1)+L_(i-1)+32, R_(i-B))
D_i = max(F_i+1352, R_(i-1))+A+1
R_i = max(D_i+879+2, F_i+L_i+41)
```

Для A=677 получаем D_i=F_i+2030 и R_i=F_i+2911 по индукции: минимальный интервал F_i−F_(i−1)=1568 даёт R_(i−1)≤F_i+1343, то есть предыдущий буфер освобождён до требуемого запуска F_i+1352. Даже при B=2 следующий повтор этого буфера не раньше F_i+3136 > R_i; имеющиеся три буфера достаточны. Период обработки при очереди **1559 ≤ 1568**, запас **9 тактов**. Это обоснование распространяется на любой порядок d=0…64 при указанных условиях. Предел A≤722 относится лишь к d≥36; для всего протокола нужен A≤686. Для других профилей меняется T; гарантия BPSK не переносится на них автоматически. При остановленном выходе дополнительные блокировки разрешены.

```sh
python3 tools/run_bpsk_uvm.py --suite all --pilot rx --profile all --output build/bpsk_uvm_rx_20261029_acq1
```

Критерии: код 0 и `status=PASS` в итоговых JSON; все прежние численные scoreboard, reset/backpressure/SIMO/конфигурация и отрицательные контроли сохраняются. `run_bpsk` дополнительно печатает `PASS BPSK divider modes: 3067 exact results, latency=66/34` для обеих полярностей. Rate — все десять строк таблицы по двум полярностям, `other_blocked=0`, `min_gap=max_gap=32`, A=677, все acquisition/output поля побитно; серии требуют ровно 480 хвостовых блокировок и 512 проверок. Численные отрицательные Questa-прогоны обязаны завершаться **13**, содержать `[NUMERIC]` и не содержать итогового положительного PASS. OQPSK проверяется из-за общего изменённого делителя, его bounds-монитор теперь считает 32 итерационных такта на запрос. Verilator macro-scoreboard не заменяет полный UVM; Questa в sandbox не запускалась (SIGSYS). Синтез и физический тайминг acq1 не запускались.

## Подтверждение Questa acq3 — PASS (2026-10-29)

`python3 tools/bpsk_rx_continuous_rate.py --backend questa --output build/bpsk_rate_20261029_acq3_gcc` завершился кодом 0 и `status=PASS` в `results.json`. Все десять строк таблицы выше воспроизвелись в Questa 2024.1: обе полярности сброса, 88 захватов, 36 352 выходных символа, 292 986 принятых отсчётов. Во всех строках **A=677**, **other_blocked=0**, **min_gap=max_gap=32**. Включены обе серии 16×192, в том числе минимальная длина кадра `d=0`. Численные отрицательные контроли завершились кодом 13; buffer guards обеих полярностей прошли.

У серии `d=0` первые отсчёты кадров действительно разделены 1568 тактами. Наблюдаемый `acquisition_done` находится на `F_i+2030`, событие `RETIRE` — на `F_i+2910`, а определённый выше первый фронт повторного использования `R_i` — на следующем такте. Это согласуется с рекуррентностью и запасом 9 тактов. Конечные серии проверены симуляцией; обобщение на произвольный порядок `d=0…64` остаётся аналитическим при указанных выше условиях. Физический тайминг не измерялся, синтез остаётся на паузе.
