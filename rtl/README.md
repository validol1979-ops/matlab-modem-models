# Потоковые RTL-модемы и DSP-блоки

Синтезируемые реализации обработки сигналов на SystemVerilog с фиксированной точкой. Для проверки используются целочисленные Python-эталоны, самопроверяющие SV-тестбенчи и UVM.

## Что это

Каталог содержит общую арифметику, память, фильтры, спектральные преобразования, средства синхронизации, адаптивные алгоритмы и кадровые модемы. Исторические модели перенесены на новый потоковый контракт: соответствие RTL целочисленному эталону и соответствие историческому MATLAB/Simulink проверяются отдельно.

Реализации Python, Octave/MATLAB и поведенческого SystemVerilog находятся вне `rtl`, в [common](../common/), [modems](../modems/) и [algorithms](../algorithms/). Поведенческие модели с вещественной арифметикой служат отдельными эталонами и не являются этим fixed-point RTL.

В документах есть результаты симуляции и прежнего размещения/трассировки на Artix-7 и Cyclone V. Их применимость определяется снимком исходников. Например, ускорение захвата PSK/QAM от 2026-10-29 проверено численно в Verilator, но его физический тайминг ещё не подтверждён. Общий статус — в [CURRENT_STATUS.md](../docs/CURRENT_STATUS.md), подробности — в [RTL_TODO.md](../docs/RTL_TODO.md).

## Как работает

1. Конфигурационный порт загружает коэффициенты, преамбулу или матрицу канала, если это предусмотрено модулем.
2. Вход принимает слово на фронте `clk` при `s_valid && s_ready`.
3. Арифметический тракт выполняет операции в заданных целочисленных форматах; округление и насыщение повторяются в Python.
4. Выход передаёт слово при `m_valid && m_ready`; `m_last` обозначает границу транзакции по контракту блока.
5. Тестбенч сравнивает принятые результаты с эталоном и отдельно проверяет паузы, сброс, границы кадров и намеренно внесённые ошибки.

Интерфейсы используют рукопожатие AXI-Stream с плоскими портами `s_*`/`m_*`, раздельными I/Q и дополнительными состояниями алгоритма. Состав портов зависит от блока; универсальной упакованной шины `TDATA` здесь нет.

| Соглашение | Значение |
| --- | --- |
| Обычный комплексный отсчёт | Две знаковые компоненты по 18 бит, 15 дробных: значение `code / 2^15` |
| Диапазон компоненты | −4…4−2⁻¹⁵ |
| Спектральные тракты STFT/PFB | 24-битный выход с 19 дробными битами |
| Фаза модемов | 32 бита; один оборот соответствует `2^32` |
| Сброс | Обычно синхронный; полярность задаёт `RESET_ACTIVE` |
| Частота стенда физической проверки | 100 МГц по [common.yaml](constraints/common.yaml) |
| Округление | Арифметические `fxp_*` — к ближайшему чётному; ряд DSP-блоков — половина вверх; точное правило указано в коде/эталоне |

При остановке выхода одни блоки замораживают конвейер, другие резервируют место в FIFO для результатов в полёте. Нельзя переносить латентность или темп одного блока на всю библиотеку. Измерения на контактах описаны в [RTL_MODEM_PIN_RATES.md](../docs/RTL_MODEM_PIN_RATES.md) и [RTL_DSP_PIN_RATES.md](../docs/RTL_DSP_PIN_RATES.md).

## Как запустить

Все команды выполняются из корня проекта. Python-зависимости перечислены в [requirements-rtl.txt](../requirements-rtl.txt): NumPy и PyYAML через основной файл требований. Python запускается без `-O`, поскольку проверки используют `assert`. Для `lint` нужен Verilator; для `hdl` — лицензированная Questa и UVM 1.2. Путь можно задать через `QUESTA_HOME`, UVM — через `UVM_HOME`; runner также ищет `vsim` в `PATH`. Для физической проверки нужны Vivado и Quartus; пути задаются `VIVADO_ROOT` и `QUARTUS_ROOT`.

```bash
python3 tools/run_rtl.py --suite python
python3 tools/run_rtl.py --suite lint
python3 tools/run_rtl.py --suite all
python3 tools/run_streaming_rtl.py --suite all
python3 tools/run_bpsk.py --suite all
python3 tools/run_cpm.py --suite all
```

Первые три команды проверяют начальную арифметику и инфраструктуру: Python, строгий lint либо Python+lint+UVM/SV. `run_streaming_rtl.py` объединяет 17 наборов FFT/DSP/OQPSK и в режимах `hdl/all` добавляет проверки мониторов протокола и насыщения; синтез он не запускает. BPSK/PSK/QAM/SIMO и CPM проверяются отдельными командами. Полные UVM-наборы перечислены в [tb/README.md](tb/README.md).

Физическая проверка и общий гейт проекта:

```bash
python3 tools/run_rtl_synth.py --block complex_mul --vendor both
python3 tools/run_tests.py --suite rtl
```

`run_tests.py --suite rtl` включает вендорный синтез и требует соответствующих инструментов; это существенно шире отдельной симуляции. Длительность полной серии зависит от инструментов и выбранных блоков, единого времени выполнения в контракте нет.

## Что смотреть

Результаты появляются в `build/rtl/`: `<suite>_results.json`, каталоги блоков, векторы, журналы компиляции и симуляции; синтез — в `build/rtl/synth/`. Для начальной инфраструктуры файл полного результата — `build/rtl/all_results.json`, для объединённого потокового набора — `build/rtl/streaming/all_results.json`.

Принимать следует завершённый `status: PASS` с `completed_at_utc`, `source_hashes` и хешами артефактов. Старый PASS после изменения исходников не является текущим доказательством; проверки свежести реализованы в [regression_evidence.py](../tools/regression_evidence.py). В положительном UVM-прогоне требуются нулевые `UVM_ERROR/UVM_FATAL`; отрицательные контроли, наоборот, должны обнаружить заданную ошибку.

Битоточное сравнение измеряет совпадение кодов RTL и Python. SER — доля ошибочных символов полезной нагрузки, BER — доля ошибочных битов; шумный канал может давать ненулевую SER при успешной проверке RTL. События насыщения и границы промежуточных выражений проверяются отдельно. Обзор: [RTL_CONTRACT.md](../docs/RTL_CONTRACT.md), [RTL_PRECISION.md](../docs/RTL_PRECISION.md), [RTL_COVERAGE.md](../docs/RTL_COVERAGE.md). [Интерактивный визуальный отчёт](../docs/visual/index.html) и [типизированный отчёт](../docs/typed_visual/index.html) показывают алгоритмические результаты; они не заменяют проверку RTL.

## Ограничения

Полное совпадение с историческим расписанием Simulink не заявляется. Известная преамбула, ограниченная длина кадров и фиксированные числовые форматы входят в новые контракты. Проверка CDC симуляцией не доказывает устойчивость к метастабильности; назначение выводов синтезной обвязки не является проектом платы. Аппаратная проверка на плате не следует из результатов симуляции или STA.

Исторические исходники не входят в публичную версию. Для OFDM происхождение, размер и SHA-256 записаны в `model.json`; у исторических модемов `source_parameters.json` хранит извлечённые параметры, а путь происхождения и SHA-256 — в `config.json` (размер в этих файлах не указан). Конкретные ссылки приведены в README модемов. MATLAB-проверки оригиналов и повторное получение исходных захватов доступны только при наличии этих материалов и требуемых MATLAB/Simulink-компонентов. После удаления сторонних файлов старые свидетельства с их хешами требуют нового прогона на публичном составе репозитория.
